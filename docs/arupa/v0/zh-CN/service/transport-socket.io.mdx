---
title: "Socket.IO"
description: "在服务中处理 Socket.IO 命名空间和事件。"
---

Socket.IO 允许服务通过内核的 Socket.IO 服务器接收和发送实时事件。适用于需要持久客户端连接、事件通知或服务端主动更新的交互式功能。

服务注册一个 socket.io 传输，然后为其绑定一条路由，声明命名空间以及它处理的事件。内核拥有该 Socket.IO 连接，负责应用访问策略，并将声明过的事件转发给该服务。

## 注册一个 socket.io 传输并绑定路由

socket.io 传输除了 `id` 之外不需要任何特定于类型的配置。绑定到它的路由携带命名空间的声明：

| 属性 | 含义 |
| --- | --- |
| `transport` | 该 socket.io 传输的 `id`。 |
| `namespace` | Socket.IO 命名空间，例如 `/my-service`。 |
| `events` | 该服务在此命名空间中接受的事件名称。 |
| `access` | 该命名空间的可选访问策略。 |
| `event_access` | 针对单个事件的可选访问策略。 |

具体的声明语法取决于所用的语言和生成的 SDK。以下是一种与语言无关的声明形式：

```text
transport: events
namespace: /my-service
events:    [update, refresh]
access:    <可选策略>
```

命名空间名称在所有正在运行的服务中必须唯一。请使用您服务专属的命名空间，通常放在服务专属的路径下，以避免冲突。关于路由和传输之间的一般关系，请参阅[路由与传输](./routing)。

## 连接到一个命名空间

客户端连接到路由所声明的命名空间。内核会在连接握手期间检查服务级和命名空间级的访问策略。只要有一个策略拒绝该用户，连接就会被拒绝。

当没有正在运行的服务拥有某个命名空间时，该命名空间不可用。停止拥有该命名空间的服务，会断开所有连接到该命名空间的现有套接字；在该服务再次启动之前，后续的连接都会被拒绝。

## 接收一个事件

只有 `events` 中列出的事件名称会被转发给服务。未声明的事件会被内核忽略。

发送给服务的事件是[协议](./protocol)中描述的 `SocketEvent` 消息，其字段包括：

| 字段 | 定义 |
| --- | --- |
| `route_id` | 拥有该命名空间的已注册路由。 |
| `namespace` | 接收到该事件的命名空间。 |
| `event` | 事件名称。 |
| `socket_id` | 发送该事件的套接字 ID。 |
| `payload` | 事件参数的 JSON 编码数组。 |
| `user` | 已认证的用户（如果有）。 |

内核不会对 `payload` 强加任何应用层 schema。请在您的客户端和服务之间定义好负载的结构，然后在服务中解码并校验它。由于负载是一个数组，带有一个对象参数的事件在概念上表示为：

```json
[{"id": 42, "enabled": true}]
```

未经身份验证的事件没有 `user` 值。

## 发送一个事件

服务使用 emit 指令发送事件。一条 emit 指令包含：

| 字段 | 定义 |
| --- | --- |
| `namespace` | 要在其中发出该事件的命名空间。 |
| `target` | 定向发送时的套接字 ID。留空表示向整个命名空间广播。 |
| `event` | 发送给客户端的事件名称。 |
| `payload` | 事件参数的 JSON 编码数组。 |

事件处理程序可以在其响应中返回一条或多条 emit 指令。这是一种可移植的请求/响应形式。对于 WASM 服务而言，这是响应传入事件时发送事件的常规方式，因为其处理程序无法主动、自发地推送事件。gRPC 服务在需要于当前处理程序调用之外发送事件时，也可以使用 Host 的 emit 能力。

对于定向事件，请将 `target` 设置为接收方套接字的 ID；对于命名空间广播，请将 `target` 留空：

```text
namespace: /my-service
target:    <socket id>   # 定向事件
event:     update
payload:   [{"status": "ready"}]
```

同样的负载规则也适用于发出的事件：`payload` 必须包含一个 JSON 参数数组。空负载会发出一个不带参数的事件。

## 访问控制

内核会在连接时和事件发生时都评估访问权限：

1. 服务级策略必须允许该用户。
2. 命名空间策略必须允许该用户。
3. 如果该事件在 `event_access` 中有对应条目，该事件策略也必须允许该用户。

所有适用的策略都必须允许该操作。命名空间策略不会覆盖更严格的服务级策略，事件策略也不会让一个受限的命名空间变为公开。

当某个套接字已经连接、但某个事件被拒绝时，内核会向该套接字发出一个 `error` 事件，说明是需要身份验证还是该用户被禁止访问。该事件不会被转发给服务。关于策略模型，请参阅[访问控制](../kernel/config-access)。

## 命名空间冲突与生命周期

一个命名空间在同一时间只能有一个拥有者路由。如果另一个正在运行的服务已经拥有该命名空间，内核不会连接新的路由。

命名空间冲突只影响该次注册：服务仍会继续运行，但内核会将其标记为 `degraded`。其他没有冲突的路由仍然可用。解决冲突并重新注册该路由，即可重新获得该命名空间。

停止一个服务会释放其命名空间的所有权，并断开所有连接到该命名空间的套接字。再次启动该服务——或者重新注册该路由——会替换所有者，并允许客户端重新连接。

## 事件处理检查清单

加载该服务之前，请确认：

- 命名空间以 `/` 开头，且该服务专属；
- 服务期望的每个事件都列在 `events` 中；
- 客户端和服务都认同每个负载是一个 JSON 参数数组；
- 负载在被服务使用之前经过了校验；
- 命名空间和事件的访问策略保护了预期的用户；并且
- 发出的事件使用了正确的命名空间和目标。

对于面向连接、事件驱动的行为，请使用 Socket.IO；对于请求/响应交互，请使用 [HTTP 传输](./transport-http)；对于可以原样提供的文件，请使用 [static 传输](./transport-static)。
